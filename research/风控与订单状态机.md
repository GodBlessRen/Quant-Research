# 风控熔断与订单一致性

> **研究者独立校勘** · 对照原书第15、19、20、21课。核心问题不是如何写出 `if drawdown > 15%`，而是**发生熔断之后，哪些动作被允许、哪些结果仍然未知**。

## 1. 熔断是动作准入，不是“一律拒单”

单纯写成下列代码存在实质风险：

```python
if current_drawdown >= 0.15:
    return REJECT
```

因为它没有区分“新增风险”和“削减风险”。当组合回撤触及阈值，若所有订单一律拒绝，策略可能连平仓或减仓都无法执行。

较安全的不变量：

```
熔断开启  ⇒  拒绝风险增加动作
熔断开启  ⇒  允许经过持仓核验的风险降低动作
强制减仓  ⇒  必须独立生成指令，并确认最终成交
```

需要注意：有些订单表面上是 `SELL`，却可能增大空头敞口；“卖出”不等于“减风险”。实际判定应当综合持仓、品种、方向、名义金额、Delta/Greeks、组合因子暴露以及跨账户净额约束。减风险的判定本身也需要特定风险模型，不能靠固定买卖方向代替。

## 2. 订单与意图不是同一个实体

建议至少把以下对象分别记录：

| 对象 | 作用 | 一等状态 |
| --- | --- | --- |
| Signal | 研究模块提出交易意图 | 产生时点、所依赖数据、有效期 |
| RiskDecision | 风险准入的结论 | 放行/拒绝/降额、理由、当时持仓快照 |
| OrderIntent | 等待执行的目标 | 幂等键、最大数量与最大成本 |
| Attempt | 每次真实发送或重试 | 请求ID、时间、超时与未知结果 |
| BrokerOrder | 券商认可的订单 | 交易所订单号、委托状态 |
| ExecutionFill | 实际成交 | 成交编号、数量、价格、费用 |
| Position | 账户持仓 | 成交归集后实际仓位与对账状态 |

**HTTP 200 不是成交确认**。下单请求可能成功送达券商但回执丢失，也可能券商收到却被交易所拒绝。若此时直接重试，会生成重复委托。

## 3. 需要支持的订单状态机

```
Created
   │
   ▼
Submitted ─────────────▶ Rejected
   │
   ▼
Accepted
   │
   ├────────▶ PartiallyFilled ───▶ Filled
   │                  │
   │                  └──────────▶ CancelPending
   │
   └────────▶ CancelPending ─────▶ Cancelled
                        │
                        └────────▶ PartiallyFilled / Filled

Unknown：网络超时或应答丢失，先对账再重发。
```

券商提供的详细状态可能更多；以上只是教学性的最小生命周期。部分取消与成交回报可并发到达，不能假设所有事件按照理想顺序抵达。

## 4. 一份可测试的简化风控示例

```python
from dataclasses import dataclass
from enum import Enum

class Decision(Enum):
    ALLOW = "allow"
    REJECT = "reject"

@dataclass(frozen=True)
class Intent:
    current_position: int
    target_position: int

def gate(drawdown: float, limit: float, intent: Intent) -> Decision:
    """教学示例：单一非衍生品的绝对净仓位约束。"""
    before = abs(intent.current_position)
    after = abs(intent.target_position)
    if drawdown >= limit and after > before:
        return Decision.REJECT
    return Decision.ALLOW

assert gate(.18, .15, Intent(100, 150)) is Decision.REJECT
assert gate(.18, .15, Intent(100, 50))  is Decision.ALLOW
assert gate(.18, .15, Intent(0, -10))   is Decision.REJECT
assert gate(.18, .15, Intent(-20, 0))   is Decision.ALLOW
```

以上代码演示**风险增加不得放行**的方向性规则，不足以应用于实盘：它没有处理价格变化、组合风险模型、跨资产对冲、成交状态、客户权限和券商回报。一个真正的“减风险订单”必须在应用实际仓位和全部未成交委托后核验。

## 5. “Unknown Outcome” 为什么应是一等状态？

假设向券商发送了卖出 100 股的请求，5 秒后本地连接超时。系统不知道订单是否已生效：

- 直接认定失败并重试，可能卖出 200 股；
- 直接认定成功，可能实际一股也没卖；
- 冻结所有行为，又可能错过风险释放窗口。

正确方向：使用稳定的客户端订单标识（若券商支持）、委托查询、成交回报和持仓对账，建立**恢复后的事实依据**。具体恢复策略受券商 API 和交易场所语义约束，不能简单宣称“重试天然幂等”。

## 6. 研究门禁、风险门禁与执行门禁分离

```
Research Gate   该策略是否有足够证据？
Risk Gate       这笔动作是否符合账户与组合约束？
Execution Gate  当前行情/成交环境是否允许安全执行？
Reconciliation  真实订单与仓位最终发生了什么？
```

LLM 可以提供风险解释或提出假设，但不能绕过确定性风险门禁。研究报告的“建议卖出”也不是一个已经经过验证的减仓动作。

## 7. 至少要做的故障注入测试

1. 触发熔断后，开仓被拒、有效减仓仍可进入风控流程；
2. 停牌、涨跌停导致订单无法执行，风险系统持续暴露未成交状态；
3. 下单应答超时，但交易所实际已接受订单；
4. 部分成交后系统重启，恢复成交数量和剩余委托；
5. 取消请求与后续成交回报交错；
6. 多账户持仓不同步，禁止无依据认定“已减仓”；
7. 延迟、断线、API 限流和重复回调不会制造额外敞口。

> 风控不是“任何异常就返回 REJECT”，而是让系统在异常下仍能分辨什么是真实、什么仍未知，以及什么动作可安全执行。
